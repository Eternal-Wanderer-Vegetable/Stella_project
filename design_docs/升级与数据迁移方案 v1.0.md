# Stella 升级与数据迁移方案 v1.0

> 决策日期 2026-08-27。目标：把「升级」从一份需要人工核对的清单，变成 1~2 次点击。

## 0. 目标与已定决策

**操作数目标**

| 场景 | 现状 | 目标 |
|---|---|---|
| 2.x / 3.0.0 存量用户升级 | 停程序 → 解压新目录 → 手工拷 2 项（实际需 10 项）→ 重填 .env → 被告知丢弃全部记忆 | 解压 → 点「从旧版本导入」确认（**2 步**） |
| 此后每次升级 | 同上 | 解压 → 双击启动，数据自动接上（**1 步**） |

**本轮已拍板的三项**（讨论过程见 §4.3~§4.6）

1. 数据目录默认 `<安装目录>/../StellaData`，配机器级指针文件；不用 `%LOCALAPPDATA%`。
2. 空间合并走**半自动命令** `deploy space-merge`（方案 B2），不做启动时自动跟随配置改名。
3. 旧的全局用户画像归入**消息量最大的那个空间**（方案 C3），其余空间重新建立认知；孤儿行进
   `legacy_<群号>` 空间永不删除；并加溯源列 `origin_group_id` 让合并可回退。

## 1. 现状诊断

### R1 用户数据与程序在同一目录，而发布包是整目录 zip

`config/settings.py:113-140` 的所有路径都锚在 `PROJECT_ROOT`（`.env`、`memory/*.db`、
`config/spaces/`、`system_prompts/`、`data/plugins/`）。`release.yml:102-137` 用 rsync 把这些
排除后打包，因此「解压到新目录」这个动作本身就把用户与其数据分开了。

### R2 迁移清单只有 2 项，实际有 10 项

`release_assets/README-快速开始.txt:51-60` 只写了 `.env` 与 `agent_memory.db`。漏掉的每一项
都造成静默故障：

| 必须迁移 | 漏掉的后果 |
|---|---|
| `.env` / `deploy.answers.toml` | 已知：配置重填 |
| `memory/agent_memory.db` | 已知：记忆丢失 |
| `memory/stella_memory_backup.db` | 留在旧目录 → 下次迁移跳过备份（`schema.py:513`） |
| `memory/.space_assignments.json` | **最危险**：账本丢失后重新分配 `space_N`，记忆全挂在旧空间名下，表现为「一切正常但什么都不记」 |
| `memory/.last_message_cleanup` | 清理锚点归零，可能重复清理 |
| `config/spaces/*.toml` | 多群共享空间配置归零 |
| `system_prompts/*.md` | 人格被发布包的 `default.md` 覆盖或丢失 |
| `config/capabilities/*.toml` | 同上（`entertainment.toml` 是入库文件，用户可能改过） |
| `data/plugins` `data/config` `data/plugin_data` | 第三方插件及其配置、运行期数据全丢 |
| `runtime/` | 重下 100MB+；**直接拷过去反而更糟**——见 §3.4 |

### R3 schema 迁移只实现了「加列」，重命名与主键变更两版声明不迁

加列类迁移其实已经全自动（`ai_gateway.py:216` 启动时调 `ensure_v2_schema`，幂等）。卡住的是：

- **v7**：`user_profiles` 主键从 `user_id` 改为按群隔离 —— `schema.py:19-24` 记「本版不做数据迁移」
- **v8**：`group_id` → `group_shared_space` —— `schema.py:25-31` 同样声明不迁，
  `schema.py:542-551` 检测到旧库只打 error，`checks.py:381-403` 的修复提示是「把 db 移出去，
  让程序重建」

而实际发布历史是：`v2.1.1` = schema v2、`2.2.0` = schema v5，**都带 `group_id` 列**。
也就是说所有 2.x 用户升到 3.0.0 都被告知丢掉全部记忆。这就是「手动迁移数据库」的真身。

### R4 空间改名同样要求手工 SQL

`config/spaces.py:226-234`：显式 toml 与自动账本不一致时打 error，让用户手工执行
`UPDATE memories SET group_shared_space=...`（并列出另外几张表）。这是第二个手动迁移点，
且专门砸在用了多群功能的用户头上。

## 2. 总体设计

三层，按阶段落地。P0 与 P1 建议同版本发布，P2 可延后。

| 阶段 | 内容 | 解决 | 升级后操作数 |
|---|---|---|---|
| **P0** | `deploy migrate` 导入向导 + 真 schema 迁移 + `.env` 合并 + `space-merge` | 存量用户 | 2 步 |
| **P1** | `STELLA_HOME` 数据目录外置 | 杜绝复发 | 1 步 |
| **P2** | GUI 内一键在线更新 | 省掉手动解压 | 1 步（含下载） |

## 3. P0：一次性桥 —— `deploy migrate`

### 3.1 命令与流程

```bash
python -m deploy migrate [--from <旧目录>] [--dry-run] [--keep-runtime] [--yes]
```

- **自动探测**：扫同级目录与同盘常见位置，找含 `memory/agent_memory.db` 的目录，
  按 mtime 取最新候选；探测不到才要求 `--from` 或由 GUI 让用户选目录。
- **只读旧目录**：全程不写、不删、不移动旧目录任何文件。任何一步失败都能原地重跑。
- **GUI**：新增一页「从旧版本导入」，调用同一命令并展示报告（业务逻辑仍全在 Python 侧，
  符合 `stella-installer/README.md` 的既定分层）。

用户实际操作：**解压新版 → 双击 `Stella.exe` → 点确认**。

### 3.2 用户数据清单：单一真相源

`deploy/migrate.py` 里定义常量，**这是全项目「什么是用户数据」的唯一定义**，
迁移、CI 校验、P1 的目录布局都从它派生：

```python
USER_DATA = [
    ".env", "deploy.answers.toml",
    "memory/agent_memory.db", "memory/stella_memory_backup.db",
    "memory/.space_assignments.json", "memory/.last_message_cleanup",
    "config/spaces/",            # 整目录
    "system_prompts/",           # 整目录，但走「改过才保留」判定
    "config/capabilities/",      # 同上
    "data/plugins/", "data/config/", "data/plugin_data/",
]
NEVER_MIGRATE = ["logs/", "data/render_cache/", "__pycache__/", ".stella-stop-request*"]
```

**「改过才保留」判定**：`system_prompts/default.md` 与 `config/capabilities/*.toml` 是发布包
自带的文件，用户可能改过也可能没动。判定方式是拿旧文件内容哈希与**旧版本发布包里该文件的
原始哈希**比对——为此发布包需要带一份 `.stella-manifest.json`（路径 → sha256，由 release CI
生成）。命中原始哈希 = 用户没改，用新版；不命中 = 用户改过，保留旧文件并把新版写成 `*.new`
且在报告里列出。没有 manifest 的旧版本（≤3.0.0）退化为「一律保留旧文件」，另附提示。

### 3.3 `.env` 合并器 `deploy/env_merge.py`

输入：旧 `.env`（用户值）+ 新 `.env.example`（结构与注释）+ `env_schema.build_schema()`
（键名 / 默认值 / 是否废弃）+ 一张改名废弃映射表。

输出：以新模板为骨架、逐行替换成用户值的新 `.env`，外加一份报告：

- 沿用 N 项 / 新增 M 项走默认值 / 废弃 K 项已移除（列出键名与原因）/ 无法识别 J 项保留在末尾
- 敏感值（`ONEBOT_ACCESS_TOKEN` 等）只报「已沿用」，绝不打印值

逐行替换的逻辑 `init_wizard.render_env:112` 已经有了，把「向导管理的 5 个键」泛化成
「旧文件里出现过的所有键」即可，模板注释因此完整保留。顺带修掉 `__main__.py:76` 那句
「请从 `.env.bak` 里对照恢复」——`init --force` 改为走同一个合并器。

### 3.4 runtime 复用与依赖标记

`runtime/` 有 100MB+，重下很痛，但**直接拷过去比重下更危险**：`start.bat:15` 判断
`runtime\.stella-deps-ready` 存在就直接 `goto :run`，而这个标记是个空文件
（`start.bat:108-110`，由 GUI 的 `--prepare` 路径写入）。拷过去 = 新版本的新依赖永远装不上。

修法：标记文件改为存放 `requirements.txt` 的 sha256，启动时比对，不一致就重跑 pip。
`start.bat` 与 `python.rs:42` 的 `DEPS_MARKER` 两处都要改，判据必须一致。
迁移默认复用 runtime（`--keep-runtime` 反向开关用于强制重建）。

### 3.5 报告与失败兜底

迁移结束写 `migration_report.md`（GUI 直接渲染）：来源目录与版本、逐项文件结果、`.env` 合并
摘要、DB 迁移摘要（见 §4.7）、需要用户注意的事项（`*.new` 冲突、孤儿空间、画像归属）。

失败兜底：文件复制阶段失败 → 删除已写入的新目录用户数据，旧目录未被触碰，可原地重跑；
DB 迁移阶段失败 → 回滚事务并保留 §4.7 的时间戳备份，报告里给出人可读的失败原因。

## 4. P0-DB：真正的 schema 迁移

### 4.1 迁移框架改造

现在的 `_migrate()`（`schema.py:529`）是一锅端的「加列 + 建表」，用一串
`with contextlib.suppress(OperationalError)` 兜住，表达不了重命名、回填、主键变更。改成按
版本注册：

```python
MIGRATIONS: dict[int, Callable[[sqlite3.Connection], MigrationResult]] = {
    7: migrate_v7,   # user_profiles 主键改为 (space, user_id)
    8: migrate_v8,   # group_id → group_shared_space，值重写为空间名
    9: migrate_v9,   # AstrBot 会话与偏好表（现有加列/建表逻辑）
}
```

- 逐级执行，每级一个事务，成功后才把 `schema_meta.version` 推进到该级
- 每级返回结构化结果（改动行数、跳过原因、告警），汇总进报告
- 加列/建索引那套保留为「每级都跑一遍」的收尾步骤（幂等，兼容历史脏库）

### 4.2 表归属分类（**搞错一张就是静默丢记忆**）

v8 的语义变化是：归属列的值从「真实 QQ 群号」变成「空间名」。因此必须逐表判定：

| 表 | 归属 | 迁移动作 |
|---|---|---|
| `memories` | 空间 | 改名 + 改值 |
| `memory_candidates` | 空间 | 改名 + 改值 |
| `atomic_facts` | 空间 | 改名 + 改值 |
| `user_profiles` | 空间 | 改名 + 改值 + 主键重建（§4.4） |
| `memories_fts` | 空间 | DROP + 重建 + 重灌（FTS5 虚拟表不能 ALTER） |
| `long_term_memories` | 空间 | **只改值、不改名** —— 列名至今仍叫 `group_id` 但存的是空间名（`retriever.py:451`、`consolidator.py:939-945`） |
| `memory_traces` | 两者都有 | 回填 `group_shared_space`（`trace.py:43-48` 两列并存） |
| `group_messages` | 真实 QQ 群 | **一个字都不动** |
| `messages` | 真实 QQ 群 | 不动 |
| `consolidation_state` | 真实 QQ 群 | 不动 |
| `short_term_context` | 真实 QQ 群 | 不动 |
| `proactive_state` | 真实 QQ 群 | 不动 |
| `group_runtime_state` | 真实 QQ 群 | 不动 |
| `compressor_state` `compressor_stats` `schema_meta` `astrbot_*` | 无群维度 | 不动 |

一个「凡是 `group_id` 就重命名」的脚本会写坏 `long_term_memories` 与全部按群归属的表；
`checks.py` 现有的旧库检测也只看 4 张表（`probe.py:294`），不能当作迁移的依据清单。

### 4.3 空间名映射：与 `resolve_space` 一致是硬约束

**约束**：迁移写进去的空间名，必须等于运行时 `config/spaces.py:204` `resolve_space()` 对该群
返回的值。不一致的后果是检索 `WHERE group_shared_space='casual'` 而行里存着 `'space_1'`——
查不到、不报错、不抛异常，即 `checks.py:393` 描述的「一切正常但什么都不记」。

所以映射不是可选策略，只能复用同一套三级解析：

1. 迁移已把旧目录的 `config/spaces/*.toml` 带过来（§3.2），显式命中就用该空间名
2. 否则查 `.space_assignments.json` 账本
3. 都没有 → 分配 `space_N` 并**立即写账本**（账本与 DB 必须同一次事务窗口内落盘）

对典型 2.x 用户这一步不会产生合并：`config/spaces.py` 是 2.2.0 之后才引入的（见其首次提交），
所以老用户根本没有 spaces 配置，结果必然是一群一个 `space_N`，1:1，无歧义。
合并只在用户**之后自己写 toml** 把多群划进一个空间时出现 —— 那条路径交给 §5。

实现上不直接 `import config.spaces`（它会拉起 `config.settings` 并读 `.env`，迁移时目标 `.env`
可能刚写好、常量已冻结，是 `__main__.py:85-92` 记过的坑）。改为把三级解析抽成不依赖
settings 的纯函数，`config/spaces.py` 与迁移都调它，避免两处判据漂移。

### 4.4 `user_profiles`：旧全局画像归入主空间（C3）

2.2.0 的 `user_profiles` 主键是 **`user_id` 单列**（该 tag 的 `consolidator.py:149-156`），
是一份跨所有群的全局画像；现在是 `(group_shared_space, user_id)`。一条旧画像因此没有唯一归宿。

采用 **C3：归入该用户消息量最大的那个空间**：

```sql
-- 依据：group_messages 按 user_id 分组统计，group_id 经 §4.3 映射为空间名后取 max
```

- 其余空间的该用户从零开始建立认知 —— 这与 v7 分群隔离的设计意图一致
- 报告里逐条写明：`画像 <user_id> 已归入 space_1（该用户 82% 的消息在此群），其余空间将重新建立认知`
- `group_messages` 里查不到该 user_id 的画像（历史消息已被清理）→ 进 `legacy_unknown` 空间保留，
  不丢弃、也不参与检索，报告列出

不选 C2（复制到每个空间）的原因：一份画像摊成 N 份各自演化，会出现「技术群的 Bot 一上来就带着
闲聊群的印象」，正是 v7 要消除的东西。不选 C1（丢弃）的原因：能救的数据没必要丢。

主键重建走 SQLite 标准三步：建新表（用 `USER_PROFILES_TABLE_DDL` 这个单一真相源）→
`INSERT ... SELECT` 带去重（同 `(space, user_id)` 冲突时取 `interaction_count` 大者，
并把两条的 `personality_traits` 并入报告供人工核对）→ `DROP` 旧表 → `RENAME`。

### 4.5 孤儿行：`legacy_<群号>` 空间，永不删除

旧库必然有 `group_id` 为空、为 `0`、或群号已不在 `ALLOWED_GROUPS`（用户退群了）的行。
策略：映射为 `legacy_<群号>`（空值归 `legacy_unknown`），**永不删除**，报告里列出行数与群号。
用户想启用只需加一个 toml 把它并进现有空间（走 §5 的 `space-merge`）。

不静默丢弃的理由：这类行数量通常不小，丢了事后无法解释，也无法恢复。

### 4.6 溯源列 `origin_group_id`：让合并可回退

空间合并本身不可逆：`space_1` + `space_2` → `casual` 之后，没有任何信息能把两群的记忆拆回来。

低成本保险：给 `memories` / `memory_candidates` / `atomic_facts` / `user_profiles` 加一个可空列
`origin_group_id`。迁移时填入该行原本的真实群号；新写入的行由 pipeline 顺手填当前群号。
属于已有的 additive 体系（`_ADDITIVE_COLUMNS`），风险极低，收益是：

- 将来「拆分空间」成为可做的操作
- 排查「这条记忆到底来自哪个群」不再靠猜（`memory_traces` 只覆盖有 trace 的那部分）

### 4.7 备份、校验、回滚

- **备份**：迁移前把库复制为 `agent_memory.db.pre-v<目标版本>-<时间戳>.bak`。
  这是独立于 `stella_memory_backup.db` 的一份 —— 后者的「已存在就跳过」语义（`schema.py:513`）
  在多次迁移场景下不可靠。
- **`--dry-run`**：输出将要改动的表、行数、空间名映射表、画像归属决定，不落盘。
  GUI 的确认页展示的就是这份预览。
- **迁移后校验**（任一不通过 → 回滚 + 保留备份 + 报错）：
  - 各表行数守恒（迁移只改值，不增删行；`user_profiles` 例外，去重条数须与报告一致）
  - 迁移后不存在归属列为空的行
  - 空间名集合 ⊆（显式 toml 空间名 ∪ 账本空间名 ∪ `legacy_*`）
  - `memories_fts` 重建后的行数 = `memories` 中 `status='ACTIVE'` 的行数
  - 随机抽 20 条记忆，用 `retriever` 的真实查询路径确认可召回

FTS 重建可直接复用现成件：`retriever.py:257-280`（列不符就 DROP 重建）与
`retriever.py:282` `rebuild_fts_index()`，不必另写一份。

## 5. P0-空间合并：`deploy space-merge`（方案 B2）

替换 `config/spaces.py:226-234` 现在那条「请手工 UPDATE」的 error 提示。

```bash
python -m deploy space-merge --from space_1,space_2 --to casual [--dry-run]
```

- 改写 §4.2 里全部「空间归属」的表 + 重建 FTS + 更新 `.space_assignments.json` 账本
- `user_profiles` 撞主键时沿用 §4.4 的合并语义（取 `interaction_count` 大者，冲突入报告）
- 先备份，`--dry-run` 出预览，跑完出报告
- `resolve_space` 那条 error 的文案改为指向本命令，不再给裸 SQL

不做 B3（启动时自动跟随配置改名）的理由：合并会撞主键、需要明确语义，且不可逆；
让用户改一行 toml 就静默触发一次不可逆的跨群画像合并，风险与收益不对称。

## 6. P1：`STELLA_HOME` 数据目录外置

### 6.1 解析顺序

```text
1. 环境变量 STELLA_HOME
2. 机器级指针文件 %LOCALAPPDATA%\Stella\home.txt（内容 = 数据目录绝对路径）
3. 安装目录本身存在 .env → 沿用旧布局（向后兼容，老用户零改动）
4. 都没有 → 创建 <安装目录>/../StellaData 并写指针文件
```

第 2 条是关键：指针文件在**程序目录之外**，所以任何一份新解压的程序都能立刻接上老数据 ——
这才是「升级 1 步」的实现基础。第 3 条保证 3.0.0 及更早的安装原地继续工作。
GUI 与 `doctor` 都要显示解析结果（`STELLA_HOME = ...`，来源第几条），否则用户找不到自己的数据。

### 6.2 目录布局

```text
StellaData/                 ← 用户数据（升级不动）
  .env  answers.toml  .stella-state.json（记录 last_run_version）
  memory/   agent_memory.db  .space_assignments.json  备份
  spaces/   *.toml
  personas/ *.md
  plugins/  plugin_config/  plugin_data/
  logs/  render_cache/
Stella-3.1.0/               ← 程序目录（升级整体替换）
  bot.py  config/  core/  memory/  deploy/  runtime/  Stella.exe
```

### 6.3 改造面

**`PROJECT_ROOT` 语义不变**（继续指程序目录），另加 `STELLA_HOME`。全项目 73 处
`PROJECT_ROOT` 引用中，只有指向用户数据的那些改基准：

- `config/settings.py` 的路径常量 —— `SYSTEM_PROMPT_PATH:123` / `DB_PATH:124` / `LOG_DIR:137` /
  `STELLA_STOP_SENTINEL:660` / `ASTRBOT_PLUGINS_DIR:671` 及其后两个插件目录 /

  **留在 `PROJECT_ROOT`**

**第三方插件兼容**：插件用 `__file__` 定位自身资源（例如

插件写数据用的是兼容层给的 data dir，只要那三个常量一起指到 `STELLA_HOME` 即可。
这一条必须用**原版未改动的插件**验证，不能用开发机里那份手工改过的副本。

### 6.4 P0 与 P1 的衔接

P1 落地后，`deploy migrate` 的目的地从「新安装目录」变为「`STELLA_HOME`」，其余逻辑不变。
所以顺序上先做 P0（清单、合并器、DB 迁移都与目的地无关），再做 P1，改动量最小。

## 7. P2：GUI 内一键在线更新（可延后）

查 GitHub Releases API 比版本 → 下载 zip 到 `.staging/` → 校验 SHA256 → 独立小进程等 GUI 退出后
换目录 → 跑 `deploy migrate`（P1 之后通常无事可做）→ 重启。有了 P1 之后这层只省掉「手动解压」。
风险集中在 Windows 文件锁与自更新，建议最后做，且保留手动解压路径作为兜底。

## 8. 防复发机制

1. **CI 校验清单闭环**：`USER_DATA` 里每个路径，要么在 `release.yml` 的 rsync 排除清单里、
   要么在 `.gitignore` 里。将来新增一个用户数据目录却忘了加进迁移清单，是本问题复发的主要途径。
2. **发布包带 `.stella-manifest.json`**（路径 → sha256），支撑 §3.2 的「改过才保留」判定。
3. **版本标记**：`STELLA_HOME/.stella-state.json` 记 `last_run_version`；现在完全没有这个东西，
   GUI 只能去 parse `pyproject.toml`（`commands.rs:267-281`）。升级判定、破坏性变更提示都依赖它。
4. **新规矩（写进 `docs/development.md`）**：`SCHEMA_VERSION` 每 +1 必须同时提交
   `migrate_vN` 函数 + 一个旧库夹具回归测试。禁止再出现「本版不做数据迁移」。

## 9. 验证策略

**必须用真实旧版本发布包验证，不能用开发机这份目录** —— 开发机的副本被手工改过，
`data/plugins/` 又是 gitignore 的，兼容层缺口正是这样漏到 release 的。

- **端到端**：从 GitHub 下 `2.2.0`（schema v5）与 `v3.0.0`（schema v9）的 zip，各自跑出带数据的
  库，走一遍 `migrate`，断言：记忆条数守恒、空间归属正确、`retriever` 能召回、人格与插件配置在位、
  `.env` 用户值全部沿用
- **夹具入库**：把上面产出的库脱敏后固化为 `tests/fixtures/legacy_db/v2.db` / `v5.db` / `v9.db`，
  进 CI 常驻回归
- **单元**：`env_merge`（沿用/新增/废弃/无法识别四类）、空间名映射纯函数、画像归属选择、
  孤儿行分类、`--dry-run` 与实际执行结果一致
- **失败注入**：迁移中途 kill 进程，确认旧目录完好且可原地重跑；DB 迁移中途失败确认回滚
