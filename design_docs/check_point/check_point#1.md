## 结论

| 窗口 | signal_score 档位 | 人工判定 | 内容性质 |
|---|---|---|---|
| 0 | 最高 | 0 条 | 角色扮演 + 二创闲聊 |
| 5 | 中高 | 0 条 | RP + 技术闲聊（当下动作，非稳定属性） |
| 10 | 中 | 0 条 | 纯 RP + 玩梗 |
| 15 | 中低 | 0 条 | RP + 阶段性状态陈述 |
| 19 | 低 | 0 条 | 纯 RP 互相吐槽 |

**当前 prompt 的 100% 空输出是正确的，不是过度修正。** 正例测试已经证明模型有提取能力（3 条明确事实全部命中），加上这五个窗口的人工基线，两边夹住了：模型现在的判断标准和你的人工判断一致。

**之前 5% 那一版是严重过度生成**——20 个窗口凭空造出 31 条记忆。按这个基线推算，那 31 条里可能有 28 条以上都是噪音。如果那个版本一直在生产环境跑，你的记忆库现在应该充满了「UID#5 自认为可爱」「UID#7 每天工作 12 小时」这类东西。

**这一轮调查的实际价值**：找到并修掉了一个正在污染生产数据的缺陷，而且是靠可量化的方式确认的（平均条数 2.35 → 1.55 → 0，空输出率 5% → 100%，配合人工基线交叉验证）。

## 但有个更根本的发现

**你的群聊数据主体是角色扮演，而不是关于真实用户的对话。**

五个窗口里 `#NAME_1` / `#NAME_2` 的台词占了绝大多数篇幅。这意味着：

- 「把群聊转成用户认知」这个设计目标，在**这个群**的数据上可提取信息极少
- 记忆系统再精确，也是精确地什么都不记
- 你的 `signal_score`（长句数减图片数）在 RP 群里完全失效——RP 台词恰好长句密集但零属性

这不是坏消息，但它改变了优先级。有三个方向可选：

**方向一：换数据源。** 你有多个群吗？技术讨论群、工作群的信息密度会高得多。`ALLOWED_GROUPS` 加一个信息密度高的群，重新采样。

**方向二：接受低产出，把重点转向"@ 优先级"。** 你之前提过的设计——@ 消息应该有更高优先级被记忆。在 RP 群里，用户直接对 bot 说的话（"我的显卡是 5080""我在杭州"）是唯一稳定的信息源。那么 D 类（@ 优先级 + `source_kind` 字段）的价值远高于 A 类的被动摄入。

**方向三：识别并跳过 RP 内容。** 在 consolidator 前面加一层轻量判断，检测到大量角色扮演标记（固定角色名、第一人称扮演台词）就直接跳过整合，省掉那 40-80 秒的 LLM 调用。

## 我的建议

**先做方向二。** 理由：

- 你的 bot 在这个群里，真实认知只能靠 @ 对话获得，这是数据决定的
- `source_kind` 字段（`AT_MENTION` / `PASSIVE`）本来就在待办里，且是结构化的、可测的
- 而且它顺带解决审计问题——将来发现一批错误记忆，能立刻知道是哪条路径产生的

**方向三性价比也很高**，因为它省的是真金白银的推理时间。你现在单窗口整合 40-80 秒，而绝大多数窗口的正确答案是"什么都不记"——这些调用全是浪费。一个几十行的启发式（检测固定角色名出现频率、`😒` 这类角色专属表情、第一人称扮演句式）能挡掉大部分。

**A 类标注可以先搁置。** 现在标注的话，你的数据集会是「20 个空样本 + 1 个人工构造的正例」，这个分布没法训练也没法评估。等换了数据源或者攒够 @ 对话之后再做。
