# Stella 插件接入规范落地方案 v1.0

> 决策日期 2026-09-01。目标：把「装完插件还得有人手写 `config/capabilities/<域>.toml`」
> 这一步收进插件自己，并让规范可生成、可校验、可查询、可热重载。

## 0. 背景与已定决策

Stella 今天能跑现成的 AstrBot 插件，但**只有一半**：`@command` 装完就能用，`@llm_tool`
注册的函数工具默认**从来不会被聊天触发**。原因不是 bug，是设计——`ROUTER_ROUTE_AUTO_CAPABILITIES`
默认 `false`，未声明的工具虽然照常注册，却不进 `registry.routable()`，而 Router 三级
（L0 关键词 / L1 embedding / L2 兜底）都以 `routable()` 为候选集来源。

这条设计有实测依据（`config/capabilities/entertainment.toml` 头部注释与
`design_docs/logs/log_2026_8_25_1303.md`）：AstrBot 的工具 `description` 是写给「看着全部
工具做选择」的决策器的**指令句**，而 Router 拿它和用户的**问句**算余弦。12 条用例对照——

| 原型语料 | 工具假阳 | 首位选错 | 无关工具被执行 | 负样本阈值余量 |
|---|---|---|---|---|
| 工具描述（原版插件现状） | 1 | 2/5 | 13 次 | **−0.024** |
| 中文问句 examples（声明） | 0 | 0 | 0 次 | **+0.141** |

所以缺口是**数据缺口（缺中文问句语料），不是 API 缺口**。代价落在用户头上：装完插件还得
有人手写声明（README:202 那一步），否则现象是「插件装了、日志说派生成功了、可就是从来不
被调用」。

**本轮已拍板的七项**

1. **Stella 插件 = AstrBot 插件 + 可选附加文件**（超集，加法）。不新增基类、不新增加载器，
   `astrbot_compat/` 那 5000 行全部复用；按 Stella 规范写的插件反过来仍能在 AstrBot 上跑。
   讨论过程见 §0.1。
2. **声明写在插件根目录 `capability.toml`**，格式与 `config/capabilities/*.toml` 完全一致。
3. **有 `@llm_tool` 却没带声明**：运行期照旧放过（不可路由 + 启动 WARNING 点名），
   `deploy plugin-check` 报 **error**。
4. **三层优先级：用户 > 出厂 > 插件自带 > 自动派生**，同一工具被高优先层认领后低优先层整条跳过。
5. **声明可以生成，但生成物必须过人审才生效**（§2）。
6. **能力对用户可见**：群里能问、CLI 能查、状态接口能读（§3）。
7. **热重载是调试功能，默认关闭**，且文档要写清它清不掉什么（§4）。

### 0.1 为什么是超集，而不是另立一套原生格式

问题的提法是：「我们的工作流先用 embedding 判定要不要调工具/调哪个工具，这对原生支持
AstrBot 的插件有什么影响？」逐条拆开：

- **指令通路完全不受影响。** `@command` / `@command_group` / `@regex` /
  `@event_message_type` 走 `plugin_handler`（priority 2），唤醒判定照搬上游
  `WakingCheckStage`——逐个 handler 跑 filter，embedding 根本不参与。
- **唯一的实质影响在 `@llm_tool` 这条路上，且是「默认失联」。** 见上文。
- **不能直接把开关打开。** 这不是翻译问题而是**用途错配**：指令句 vs 问句。首轮实测（5 个
  bgm/bilibili 工具）对一句「主管，这是？」给出 0.443 / 0.412 / 0.388 / 0.386 / 0.385，
  彼此差不到 0.06，而当时置信线 0.45——差 0.007 就要凭空调工具；「这个游戏怎么样」拿到
  0.474，直接越线。
- **同域插件会「搭车」。** 「帮我推荐一些新番」里正确能力 0.911，而每日放送 / B 站热门
  0.689 / 0.678——高于任何可用的绝对地板。每个命中能力**各执行一次**，结果都贴进 prompt 的
  证据段，所以搭车不是多花点延迟，是往证据里塞无关数据。`ROUTER_CAPABILITY_MARGIN` 为此而加。
- **装工具的成本结构反了。** AstrBot 里装 N 个工具 = 每次请求都把 N 份 schema 塞进上下文
  （token 线性涨）；Stella 里 = N 个原型向量（一次性编码 + 按注册表版本落盘缓存），对话
  窗口不涨——README 那句「插件装再多，占的也不是对话窗口」就是这个机制。代价换成了
  「N 越大，同域混淆概率越高」。
- **`description` 这个字段降级了。** 在 AstrBot 里它是决策依据；在 Stella 里写了声明它只是
  原型语料里的一条（和 examples 一起取均值），没写声明它就是唯一语料——而它不胜任这个用途。

**结论**：embedding 先判定造成的缺口是数据缺口，不是 API 缺口。原版插件的基类、装饰器、
事件、组件、配置 schema、渲染，与 Router 完全正交——另立原生格式不会让路由准一分，唯一能
让它变准的是 examples 语料，而那份语料可以作为一个可选文件挂在一个**完全没改过**的 AstrBot
插件旁边。反过来，超集还能做原生格式做不到的事：**我们替流行插件写声明**
（`config/capabilities/entertainment.toml` 已经是这么干的——那是给 `astrbot_plugin_bilibili`
手写的，插件作者全程没参与）。

## 一、三层声明的加载机制

### 1.1 `capability/loader.py`

现在 `load_capabilities()` 在两个目录间**二选一**：

```python
directory = STELLA_HOME / "config" / "capabilities"
if not directory.is_dir():
    directory = PROJECT_ROOT / "config" / "capabilities"
```

这是个隐坑：用户目录里只要出现一个文件，出厂声明（含随仓库发布、带实测标定的
`entertainment.toml`）就**全部失效**，而这不报错、只表现为路由变差。加第三层时一并改掉。

- `load_capability_file(path, target, *, source="config", skip_claimed=False)`
  —— `source` 落到 `CapabilityProvider.source`；`skip_claimed=True` 时注册前逐条判定
  「该 id 已存在」**或**「任一 provider 的工具名已被别的能力认领」，命中则**整条跳过**并记
  INFO（说明被哪一层顶掉）。整条跳而不是跳单个 provider：半条能力的 examples/keywords 与
  providers 不再自洽，比缺一条更糟。
- `load_plugin_capabilities(target=None)`：只扫**成功加载**的插件（遍历
  `astrbot_compat.registry.star_registry` 取 `md.root_dir_name`，拼
  `ASTRBOT_PLUGINS_DIR / <dir> / "capability.toml"`），`source="plugin"`、`skip_claimed=True`。
  **必须只扫已加载的**：import 失败的插件没登记任何工具，它的声明会造出 provider 指向不存在
  工具的能力——`routable()` 只查 enabled/backoff、不查工具是否存在，于是它会参与路由竞争、
  抢走 `ROUTER_CAPABILITY_MARGIN` 的间距，最后在 Comes 里必然 failed。
- `load_declaration_tiers(target=None) -> dict[str, int]`，按序执行并返回每层计数：

  | 序 | 层 | 位置 | source | skip_claimed |
  |---|---|---|---|---|
  | 1 | 用户 | `STELLA_HOME/config/capabilities/` | `config` | `False` |
  | 2 | 出厂 | `PROJECT_ROOT/config/capabilities/` | `config` | `True` |
  | 3 | 插件自带 | `<已加载插件>/capability.toml` | `plugin` | `True` |

  两个目录 `resolve()` 后相同时（开发机、自包含布局）只走一次。

### 1.2 `capability/registry.py`

- 加 `SOURCE_PLUGIN = "plugin"` 常量；`Capability` 加 `source: str = ""`，**仅供诊断展示与
  校验**，不参与任何路由逻辑。
- 新增 `unregister(capability_id) -> bool` 与 `release_tool(tool_name)`（今天只有 `clear()`）。
  热重载要用（§4）。**必须同时清 `_claimed_tools`**：否则重载后工具永远被一个已不存在的能力
  认领着，新声明抢不到 → 静默失效。

### 1.3 `capability/adapters/astrbot.py`

`bootstrap()` 把 `load_capabilities(target=target)` 换成 `load_declaration_tiers(target)`，
统计加 `plugin_declared`。**顺序仍不可交换**（声明必须早于自动派生），docstring 那段理由照旧
成立，补三层说明。`sync_astrbot_tools()` 那条 WARNING 文案加第三条出路：「或在插件目录里放
一份 `capability.toml`」。

### 1.4 新增配置

`ASTRBOT_PLUGIN_CAPABILITIES_ENABLED`（默认 `true`）。

为什么要有这个开关：插件自带声明意味着**插件作者**决定自己的工具能在聊天里被自动调用，而
今天这件事需要用户手写 TOML 才成立——那是一次显式的、逐工具的授权。默认打开是因为零配置
是本规范的意义所在；留开关是因为「谁决定我的 Bot 会调什么」应当能被用户收回。装配日志必须
点名哪些能力来自插件层。

改 `config/settings.py` 需按现有惯例同步 `.env.example`，说明注释写在键上方（GUI schema 从
注释生成）；`tests/test_env_schema.py` / `test_env_merge.py` 覆盖这条链路。

## 二、`capability.toml` 半自动生成

> **一处需要说明的取舍**：`capability/adapters/astrbot.py` 与 `docs/capability-system.md`
> 原本都写着「这个局限**刻意不用生成的方式去补**……生成质量无法验证，错的 examples 比没有
> examples 更糟」。那条结论针对的是**运行期、无声、无人过目**的生成（启动时调模型直接把
> examples 灌进内存里的原型向量）。本节做的是另一件事：**离线生成一份磁盘上的草稿，人审
> 之后才生效，且交付时附上量化指标**。「质量无法验证」在有文件、有审阅、有基准的前提下不
> 成立。原结论的实质（未经验证的语料不许进路由）由下面的 `reviewed` 闸门保留。这两处文档
> 要跟着改写，不能留着自相矛盾。

### 2.1 `python -m deploy plugin-scaffold <插件目录>`

新增 `deploy/plugin_scaffold.py`。产物是 `<插件目录>/capability.toml.draft`。

**喂给模型的不只是工具描述**（那正是质量差的根源）。可用输入按信息量排序：

1. 插件 `README.md`（通常带真实使用示例，最好的语料来源）
2. `@command` 的指令名与说明（`/天气` 本身就是自然说法）
3. `@llm_tool` 的 docstring `Args`——参数名与说明暗示用户会怎么提（必填 `city` → 说法带城市）
4. 工具 `description` 与工具名
5. `metadata.yaml` 的 `name` / `desc`

**产出形态**：每个工具一条 `[[capability]]`，`examples` 填 5~6 条中文问句，`keywords`
**留空**，候选词以**注释形式**列在下面等人取用——「绝不从 examples 里猜」那条规则（中文没有
词边界，从「会不会下雨」切出来的候选里既有「下雨」也有「不会」）对生成器同样适用，模型给的
候选词必须由人确认。文件头写入 `reviewed = false`。

**模型选择**：离线、一次性、质量敏感 → 默认走 `ROLE_EXTRACT` 那一档
（`core/llm/registry.py`），`--endpoint` 可覆盖。走现有角色注册表，用量照常记账。

### 2.2 `reviewed` 闸门

`load_plugin_capabilities()` 只载入 `capability.toml`；`*.draft` **一律不载入**。
`capability.toml` 里 `reviewed = false` 时同样不载入，只记一条 WARNING 点名「有草稿待审」。
人审完把文件改名并把 `reviewed` 改成 `true`，才进注册表。

这样「错的 examples 把不相关请求吸进来」这个风险的**触发路径被掐断**——没审过的东西根本
到不了 Router。

### 2.3 生成完就能量化，不必凭信

`plugin-scaffold` 生成后直接用真实 embedding 算一遍并打印报告（复用
`memory/embeddings.py::EmbeddingService`，就是 `router/semantic.py` 在用的那个；负样本集
复用 `capability/router/benchmark` 现有用例，不另建一套）：

| 指标 | 复现的失败模式 |
|---|---|
| 同域能力两两原型余弦**分离度** | 首轮实测那个 0.443/0.412/0.388/0.386/0.385、spread<0.06 |
| 每条 example 与本能力原型的余弦 | 找出跑偏的 example（原型取均值，对个别坏句敏感） |
| 负样本最高分与置信线的**余量** | 就是对照表里 −0.024 → +0.141 那一列 |

分离度不足或负样本余量为负时明确报出来，并指出该删/该改哪条 example。这条是本节的核心：
它把「生成质量无法验证」变成一个可打印的数。

## 三、能力查询：让人知道 Stella 现在会什么

三个 surface，同一份数据源。

### 3.1 群里问

照 `ai_gateway.py` 里 `toggle_handler` 的现成惯例（`on_message(rule=Rule(...), priority=1,
block=True)` + `_record_bot_lines` + `finish`）加一个 `capability_handler`：

- 触发：已启用群 + @ 机器人 + 命中「你能做什么」「有什么功能」「能力列表」等
- 回复：按 domain 分组列出**可路由**的能力（一句话描述），末尾一行说明「另有 N 个插件工具
  未配声明，不会被自动触发」
- **权限**：普通群友可查——「让用户知道」是这条需求的全部意义。来源层、provider 健康度、
  未声明工具的具体名单属排查信息，只给管理员（同 `PROACTIVE_TOGGLE_ADMINS` 或群主/管理员）
- 长度超限时用 `astrbot_compat.render.render_text` 出图（本地 Chromium，已有），失败退纯文本截断

**优先级不变量**：`ai_gateway.py` 有个 `_assert_listener_priorities()` 启动自检，钉住
`group_silent_listener < toggle(1) < plugin(2) < chat(3)`。新 handler 必须进这个自检，
否则「你能做什么」会被当普通对话交给 LLM。与 `toggle_handler` 同优先级时两者的 rule 必须
互斥（都是 `block=True`）。

### 3.2 CLI：`python -m deploy capabilities [--json]`

注册表是**进程内**的模块级单例，外部进程拿不到——所以照 `deploy status` 的做法走状态接口
（`GET /stella/status`，回环 only，见 `deploy/process.py::_fetch_live_status`），
在 `status_api.py::build_payload()` 里加一个 `capabilities` 块。

**payload 只放结构化字段**：`id` / `domain` / `source` / `route_enabled` / provider 工具名 /
工具是否真的存在 / 退避状态 / `examples` 条数。**不放 `description` 与 `examples` 原文**——
`tests/test_status_api.py` 钉住了「响应体不含凭据与群聊内容」，而自由文本是唯一可能夹带
URL/密钥的字段，不放进去就不用为它加一道守卫。原文本地可读（CLI 直接读那三层 TOML）。

CLI 渲染成表：哪些能被聊天触发、哪些不能、各自来自哪一层、哪个 provider 正在退避。
这张表就是今天「插件装了但从来不被调用」的直接答案。

### 3.3 GUI

复用同一个 payload，加一个只读列表。工作量在 `stella-installer/`（Tauri，原生 HTML/JS），
放到最后一期做，前两个 surface 已覆盖用户与排查需求。

## 四、插件热重载（调试用，默认关闭）

`astrbot_compat/loader.py` 新增 `async def reload_plugin(dir_name) -> StarMetadata | None`：

1. 按 `root_dir_name` 找 md
2. `await md.star_cls.terminate()`，5s 超时（照 `terminate_plugins`，注意 Py3.10 下必须写
   `asyncio.TimeoutError`）
3. 摘 handler：`get_handlers_by_module_name` 要对 `md.module_path` **及其子模块前缀**都取
   （handler 可能定义在插件包的子模块里——`base.py::_resolve_plugin_dir_name` 正为此做了前缀
   匹配），逐个 `star_handlers_registry.remove(h)`
4. 摘工具：从上一步 handler 里挑 `event_type == OnCallingFuncToolEvent`，工具名取
   `extras_configs.get("tool_name") or handler_name`，`llm_tools.remove_tool(name)`
5. 摘能力：`registry.unregister()` + `release_tool()`（§1.2 新增）
6. 摘模块：pop `pkg` 及所有 `pkg.` 前缀的 `sys.modules` 项；pop `star_map[module_path]`；
   从 `star_registry` 移除 md；清 `_loaded_dirs` / `_failed` / `_alias_dirs` 对应项
7. `load_plugin(dir)` + `await initialize()`
8. 重跑该插件的声明层 + `sync_astrbot_tools()`。`registry.version` 自增会让 `semantic` 的
   原型缓存自动失效（已有机制），再后台 `warmup()`

**清不掉的东西——必须写进规范，也必须在重载回复里说**：

- 插件在 `__init__` / `initialize` 里**裸调** `asyncio.create_task(...)` 起的任务。
  `Context._tasks` 只登记走 `register_task` 的那些，而且是全局一张平表、没有归属标记，
  所以裸 task 重载后会**残留并继续跑**（`astrbot_plugin_bilibili` 就是裸 create_task）。
  两条出路：给 `register_task` 加归属标记并在规范里要求插件走它（推荐，是个规范条目），
  或者承认泄漏。
- 插件起的线程、注册的全局钩子、monkeypatch、第三方库的模块级状态、已被别处持有的旧实例引用

因此定位是**调试便利，不等于重启**；规范里明说「怀疑状态不干净就重启」。

**开关与触发面**：`ASTRBOT_PLUGIN_HOT_RELOAD_ENABLED`（默认 **false**）。

- 触发用**群内管理员命令**（`@Stella 重载插件 <名>`），复用 `toggle_handler` 那套权限模型。
  选它是因为不必给状态接口开一个能执行任意插件 re-import 的 POST——那是比只读端点大一档的
  安全步骤。
- 可选：`ASTRBOT_PLUGIN_HOT_RELOAD_WATCH`（默认 false）监视插件目录 mtime 自动重载。
  调试最省事，但「自动」在生产上危险，跟主开关一起默认关。

## 五、校验工具：`python -m deploy plugin-check <插件目录>`

新增 `deploy/plugin_check.py`，复用 `deploy/checks.py` 的 `CheckResult(id, level, title,
detail, fix_hint)` 与 `deploy/report.py` 的渲染；`deploy/__main__.py` 加子命令（`--json` 供
GUI，有 error 时退出码非零）。命名跟 `config-schema` / `space-merge` 的连字符惯例。

需要 import 插件才能枚举工具——这与启动时 `loader.load_plugin()` 做的事同类，不是新的风险面，
但要在输出里明说「已执行该插件代码」。

| # | 检查项 | 级别 | 依据 |
|---|---|---|---|
| 1 | 缺 `main.py` / 目录里是未解压的压缩包 | error | `discover_plugins`、`unextracted_archives` |
| 2 | shim 下 import 失败 / 无 `Star` 子类 / `initialize()` 抛异常 | error | 复用 `_import_failure_reason` 的话术 |
| 3 | `requirements.txt` 里的包在当前环境缺失 | error | 带上 `pip install -r` 命令 |
| 4 | **有 `@llm_tool` 工具未被任何声明的 `providers` 认领** | **error** | 决策 3 |
| 5 | 声明的 `providers` 出现 `llm_tools` 里不存在的工具名 | error | 工具名拼错是静默失效的头号原因 |
| 6 | 只有 `capability.toml.draft` / `reviewed = false` | error | §2.2 闸门；提示跑人审 |
| 7 | `examples` 少于 3 条 | warn | 实测 4~6 句才稳 |
| 8 | `examples` 疑似指令句（命中「当用户」「时调用」「本工具」「用于」） | warn | 用途错配是整条设计的起点 |
| 9 | `keywords` 里的词是某条 `example` 的子串 | warn | 「绝不从 examples 里猜」的机械化 |
| 10 | `keywords` 出现短于 3 字的词 | warn | 「新番」vs「番剧推荐」那个教训 |
| 11 | 工具有必填参数却给了 `keywords` | warn | L0 取不出参数，拍板只是让 Comes 去猜（`anime.search` 不给 / `video.dynamics` 破例，正反两例都在 `entertainment.toml` 里） |
| 12 | 同域能力原型分离度不足 / 负样本余量为负 | warn | 复用 §2.3 的量化，两处同一份实现 |
| 13 | 能力 id 或工具与用户/出厂层撞名 | info | 明确告知会被哪一层顶掉 |
| 14 | 源码出现 `url_image(` | warn | `html_render` 返回本地路径，`url_image` 会 ValueError |
| 15 | 裸 `asyncio.create_task(` 而未走 `context.register_task` | warn | §4 的泄漏边界 |
| 16 | import 了 httpx/aiohttp/requests 但 metadata 未声明 `stella.egress` | warn | 纯披露，见 §6 第 10 章 |

第 16 项（及其 `stella.egress` 规范条目）是**最容易裁掉**的一项。

## 六、规范文档 `docs/plugin-spec.md`（+ `.en.md`）

双语成对，与 `docs/` 下其余五份一致。章节：

0. **适用范围与兼容性承诺** —— Stella 插件 = AstrBot 插件 + 可选附加文件；双向兼容；明说
   「不保证全量插件可用」（照 `astrbot_compat/__init__.py` 的措辞）
1. **最小可跑插件**（20 行骨架）
2. **目录结构清单** —— 表：文件 / 必需性 / 作用 / AstrBot 是否也读
3. **两条接入通路怎么选** —— 决策树。**可路由能力必须是只读/幂等的**：Comes 不经用户确认
   就会调工具，会发消息、下单、改外部状态的一律走 `@command`
4. **生命周期与加载时机** —— 在事件循环内装载，所以 `__init__` 里 `create_task` 是允许的；
   但**要走 `context.register_task`**（热重载与退出时才收得回，见 §4）；`initialize` /
   `terminate`（5s 超时）
5. **指令通路规范** —— `ASTRBOT_WAKE_PREFIXES`（默认 `/`）、私聊、`should_dispatch()` 的把关
6. **工具通路规范（核心）**
   - 6.1 `@llm_tool` 签名与 docstring `Args` 契约（`parse_tool_docstring` 是唯一的参数来源）
   - 6.2 `capability.toml` 字段语义 + 三层优先级 + `reviewed` 闸门
   - 6.3 **怎么写 `examples`** —— 写「用户会怎么问」，4~6 句，附背景那张对照表；以及
     **怎么让 `plugin-scaffold` 替你写第一版**
   - 6.4 **怎么写 `keywords`** —— 名词短语、宁缺勿滥、绝不从 examples 切、有必填参数就别给
   - 6.5 **返回值契约** —— `data` 全程不进 prompt，只有 `summary`（≤ `COMES_SUMMARY_MAX_CHARS`
     = 300 字符）进；返回值还要过受限 agent 自己的 8192 窗口，别甩几千字 JSON
   - 6.6 **失败契约（最容易写错的一条）** —— 失败要**抛异常**：`agent.execute_tool` 包成
     `error: ...`，`summarizer.is_error()` 据此为真，provider 健康度才会记账退避。若改成
     `return "查询失败：API 超时"`，那串字不以 `error:` 开头 → 被当成**成功输出** → 经
     summarizer 贴上「刚刚查到的信息（真实数据，回答时以此为准）」进 Stella 的 prompt，
     于是 Stella 把失败文案当事实转述给用户，**而且退避永远不触发**
   - 6.7 超时 —— `COMES_TOOL_TIMEOUT` 60s，挂在聊天主链路上，用户在等回复
   - 6.8 无参直调 —— 没有必填参数时跳过一次模型往返（`COMES_DIRECT_CALL_NO_ARGS`）
   - 6.9 一个能力多个实现：`priority` 与失败退避
7. **上下文预算契约（8K）** —— 工具描述与原始返回都不进人格 prompt；顺带讲清成本结构与
   AstrBot 的差别（见 §0.1）
8. **渲染契约** —— 本地 Chromium；返回**本地路径**；不可用时返回**空串而非抛异常**，所以
   插件必须有 `if img_path:` 降级分支；别用 `url_image`；首次 270MB 后台下载
9. **配置与数据** —— `_conf_schema.json` / `AstrBotConfig` / `StarTools.get_data_dir` / KV；
   **群与空间的分界**：插件拿不到 `group_shared_space`，要按群隔离就自己用 `group_id` 建键
10. **隐私与出网声明** —— `metadata.yaml` 的 `stella.egress`（host + purpose）。这是**披露
    契约，不是沙箱**：我们不拦未声明的请求，规范里必须这么写。Stella 的零出网承诺依赖
    「判断该不该用工具、压缩结果、渲染卡片全在本地」，而插件是唯一被允许出网的环节
11. **兼容性矩阵** —— 上游 API 全表：已实现 / 降级实现 / 抛 `StellaCompatNotSupported`
12. **自检、生成与发布** —— `plugin-scaffold` → 人审 → `plugin-check` →
    `python -m capability.router.benchmark` 的完整流水
13. **调试** —— 热重载怎么开、能重载什么、**清不掉什么**、什么时候必须重启
14. **能力查询** —— 群里怎么问、CLI 怎么查、各字段含义
15. **版本与兼容策略** —— `astrbot_version` 只告警不拦、`ASTRBOT_COMPAT_VERSION`、本规范版本化
