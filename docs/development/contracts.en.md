# Current branch contracts and release boundaries

<a id="source-contracts-and-release-gates-in-610"></a>

P04 advanced the memory source contract to schema 23/API 4 on 2026-10-25, adding append-only transport message event, part, and relation tables. The social side-table contract is schema 5, Scheduling SQL is schema 2, and Cometa Origin JSON is v3. Released assets retain their own build contracts; an older native wheel must not load a schema 23 database. Source constants are aligned, but a deployed wheel was not verified in this stage.

The values describe source compatibility, not proof that a particular wheel was built, loaded, or accepted. Recheck constants when changing branches.

- Memory schema 23/API 4 must agree in `memory/schema.py`, `memory_rust/backend.py`, and `memory_rust/native/src/schema.rs`. Validate exported constants, not just the wheel package version. v23 appends transport event/parts/relations and retains the legacy integer `msg_id` for the explicit QQ compatibility path.
- Social schema 5 stores every opaque platform message ID returned for a physical delivery part in `social_deliveries.platform_message_ids_json`. The v4→v5 migration wraps the existing primary ID in a one-item list without reinterpreting it. WP06 retains the singular compatibility field while adding complete per-part receipts.
- Scheduling schema 2 stores verifiable DeliveryTarget, subject, and scope on tasks/runs/audit/quota. Legacy QQ tasks become sendable only when the Bot/group destination can be bound unambiguously; other rows stay unroutable, and old quota is preserved in an isolated legacy scope. Sending resolves the persisted BotRef exactly; unknown results are not retried automatically.
- P05 outbound contract: `OutboundService.send` serializes a complete Bot/scene/route target in FIFO order. Each target allows at most 32 queued items; target-lane and quota state are each capped at 4096 entries. `rate_limit_buckets` enforces adapter, connection, scene, and target scopes independently alongside the separate `api` and `request` categories. Legacy rate fields map to adapter API and connection API buckets; differing windows are never collapsed into one effective limit. Rolling quota state is process-local and resets on restart. Every physical part and every retry consumes quota. Only a definite FAILED result with a standard rate-limit code and retry-after may retry, at most twice by default; one retry-after wait is capped at 30 seconds and remains bound by the message deadline/window. UNKNOWN is never replayed. Receipts retain physical-part status, attempt count, and opaque message IDs. A queued send is rejected when its exact Bot binding generation changes or disconnects. The same self_id may exist on different adapters; a conflicting slot within one adapter is rejected.
- P06-T Telegram codec: pins `nonebot-adapter-telegram==0.1.0b20` and requires explicit opt-in through `register_telegram_transport` plus a `TransportIngress` normalizer mapping; there is no default matcher or startup registration. Evidence sources are the [locked adapter source](https://github.com/nonebot/adapter-telegram/tree/v0.1.0b20) and the [Telegram Bot API](https://core.telegram.org/bots/api). Bot, user, chat, topic, and message IDs stay opaque strings in Stella contracts; sending accepts only canonical numeric chat/topic IDs and keeps the topic scoped to its chat. Private chats, groups/supergroups, and `message_thread_id` topics are supported. Reply relations point to the same connection and canonical conversation, and remain unresolved until local message lookup confirms them. Inbound media stores only type/MIME/size hints, never Telegram file IDs. Sending uses the exact Bot and `send_to(chat_id, message_thread_id=...)` receipt; explicit `ActionFailed` is FAILED, while network errors/timeouts are UNKNOWN and never replayed. Default capabilities cover only private/group/topic, reply, image, and file; user mentions and channel posts are unsupported, proactive is disabled, and no unverified rate quota is declared. The Python-character cap is 2048, conservatively below the Bot API's 4096 UTF-16-code-unit text limit. Bot API `message_id=0` is ephemeral and unusable for durable replies. The current Bot API uses a separate `direct_messages_topic_id` route for direct-messages chats; the locked 0.1.0b20 adapter does not expose it, so those messages are not certified or routed. Fixture passes do not certify Telegram live, live relation/media behavior, or permissions; the matrix stays `not_certified` pending real-account acceptance.
- P06-D Discord codec: pins `nonebot-adapter-discord==1.1.10` and is opt-in through an explicit `register_discord_transport` call plus a `DiscordNormalizer` entry in `TransportIngress`; it adds no default matcher or startup hook. The locked adapter's message events carry `channel_id` / `guild_id` but no channel type, so the normalizer requires an injected trusted `channel_resolver` and verifies channel, guild, and parent identities; absent metadata is rejected. Supported scenes are one-to-one DMs, guild text/announcement channels, and announcement/public/private threads; group DMs are unsupported. Discord IDs remain strings in Stella contracts. For a thread, `scene_id` and `thread_id` are the actual thread channel ID and `parent_path` retains guild and parent channel; sending uses that exact `scene_id` and never falls back to the parent. The normalizer checks `direct_messages` / `guild_messages`; guild content additionally requires `message_content` or an adapter-confirmed bot mention/reply. Replies accept only a DEFAULT reference in the same exact channel and remain unresolved when the referenced message is absent from the event; forwards and cross-channel replies are rejected. Edits require author, content, and platform `edited_timestamp`. Inbound attachments retain only type/MIME/size hints, never URLs or attachment IDs. The exporter supports text and reply only, sends empty `allowed_mentions`, caps Python text at 1900 characters, and marks replies `fail_if_not_exists=true`. A definite adapter `ActionFailed`, including a permission rejection, is FAILED; timeout and other uncertain outcomes are UNKNOWN and are never retried automatically. Discord validates thread-send permissions against the exact target; threads require `SEND_MESSAGES_IN_THREADS`, and a denied fixture never falls back to the parent, but this does not certify live permissions. Proactive sends, user/role mentions, uploads, and unrestricted passive capability are disabled; rate limits and send windows are not certified. The lock-pinned wheel was installed under `/tmp` only for fixtures; `.venv` was unchanged. No live Bot, permission, or driver test ran, so the matrix remains `not_certified`.
- P06-Q official QQ codec: `pyproject.toml` and `requirements.txt` pin `nonebot-adapter-qq==1.7.3`. A connection owner must explicitly call `register_qq_transport` and add `QQNormalizer` to `TransportIngress`; no default matcher, startup registration, or unrestricted passive listener is installed. Supported events are intent-enabled C2C private messages, @group messages, @text-channel messages, and guild direct messages. Unmentioned group/channel messages, threads, interactions, proactive sends, media uploads, and rich-text output are unsupported. QQ OpenIDs, message IDs, and channel IDs remain opaque strings; text-channel scenes use the exact child channel, while a guild DM scene uses its DM channel. Each `DeliveryTarget` must carry the original SDK event, the same Bot, and the exact message ID; serialized targets cannot send. Its deadline is computed from the event timestamp: 60 minutes for C2C private messages and five minutes for groups, text channels, and guild DMs. The exporter accepts plain text only, constructs an explicit SDK text segment, and calls `send_to_c2c`, `send_to_group`, `send_to_channel`, or `send_to_dms` with the source event's `msg_id`; a general message event's `event_id` is not used as a reply token. C2C and group replies use `msg_seq=1`, which the API rejects on duplicate, and expired targets never switch accounts. QQ's official policy states that proactive push has not been available since 2025-04-21; text-channel sends also require a connected WebSocket. A definite SDK `ActionFailed` is FAILED; timeout, network errors, and missing receipts are UNKNOWN and are never replayed automatically. Inbound attachments keep only safe MIME/size/name hints; signed URLs are discarded. The upstream 1.7.3 wheel source was used under `/tmp` for fixtures, while the current `.venv` still has no installed distribution. The matrix records `not_installed` and `not_certified`; no live QQ, permission, or driver acceptance ran. See [QQ send policy](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/server-inter/message/send-receive/send.md) and the [1.7.3 SDK Bot API](https://github.com/nonebot/adapter-qq/blob/v1.7.3/nonebot/adapters/qq/bot.py).
- Cometa Origin v3 stores BotRef and DeliveryTarget together and validates that they agree. v1/v2 compatibility is limited to known legacy OneBot QQ semantics; records whose target identity cannot be proven fail closed. The Cometa SQL table remains schema 1.
- `python scripts/generate_message_flow.py --check` validates source anchors, closure, and manifest. Regenerate archived topology after source changes; static reachability is not observed execution.
- Frontend checks: `pnpm --dir dashboard test` and `pnpm --dir dashboard build`. Synchronize the local bundle with `pnpm --dir dashboard sync:webui`.
- Isolated evaluation: `python scripts/run_flow_evaluation.py --mode isolated_pipeline --dataset <dataset_dir> --workdir <isolated_dir> --json`. Other modes are trace_playback, decision_recompute, and model_validation. Dataset/workdir are required; production is never a fallback database.
- `python scripts/evaluate_dialogue_attribution.py --help` describes frozen fixtures, protocol prompts, and `--guard`. Replay does not substitute for persisted identity checks or real QQ rollout.
- Synchronize the application version across `pyproject.toml`, `cli/Cargo.toml`, `desktop/src-tauri/Cargo.toml`, Tauri configuration, and corresponding locks. The native wheel, launcher, runtime-manager, and private Dashboard package retain independent component versions.
- Tag release builds the dashboard, candidate CPU backend, offline payload, wheel, CLI, and four installers. Each final EXE is validated on a Windows runner before publication. Manifests bind size/SHA-256 and published assets are read back for verification.
- The workflow defaults to `VERSIONED_LAYOUT=0`; launcher-based installer relocation is not enabled by default. Hosted Windows installation checks do not equal clean-VM/GUI-first-launch acceptance; see `release_assets/VM-MATRIX.md`.

Use the target commit's CI as current test evidence. Older counts are dated snapshots. See the [index](../README.en.md) for QQ rollout and Rust ranking boundaries.
