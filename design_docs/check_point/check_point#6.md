❌ 1. 工具假阳 1 例（项目自评"高"严重度）

- ROUTER_TOOL_THRESHOLD(0.45) 只卡最高分。一旦 tool=true，凡 ≥ ROUTER_SEMANTIC_THRESHOLD(0.35) 的命中全部随车执行。0.44 这个本身不足以触发工具的分数，作为搭车者被执行了。

❌ 2. Router 排序不正确，最高分能力对答案零贡献

用户问"推荐新番"，语义最贴的是 bgm_recommend_hot_subjects（描述："当用户想看近期热门/热度榜/最近值得看的 ACG 条目时调用"）——它排第 2，0.45 刚过线。排第 1 的 get_bgm_daily_schedule（描述："当用户询问今天或某天更新什么动画时调用"）答的不是这个问题，却吃掉了最长的 8.343s。最终回复的《无职转生》第三季和《尼古喵喵》全部来自第 2 名的结果。

二、架构选择：AstrBot 兼容层该怎么办

先纠正一个前提，因为它会直接影响选项判断。

不兼容的到底是哪一层

不是加载层和执行层——那部分是好的。 插件装上了、@llm_tool 登记了、event / bot 句柄透传到位、execute_tool 正常调用、run_tool_loop 的参数过滤和超时都在。今天日志里三个工具全部 success 就是证据。

真正不兼容的是元数据契约，一共四条：

1. description 是写给"决策器"的，被我们挪用成了"路由原型"。
AstrBot 的模型是"把全部工具 schema 塞给一个大模型，让它选"。所以描述写成 当用户询问 ——这是指令句 + 边界条件，正是给 function-calling 决策器看的最优写法。而 Stella 的Router 拿它去和用户问句算余弦。这两种用途要求的文本形态根本不同：前者要"什么时候该用我"，后者要"用户会怎么问"。
这不是 AstrBot 写得不好——我核对了 data/plugins/astrbot_plugin_bilibili/tools/*.py，五个描述都是规范中文，质量不错。是用途错配。0.44/0.41/0.39/0.39/0.39 就是错配的读数。

2. parameters.required 为空 ≠ 参数不重要。
AstrBot 的 schema 里没有"这个可选参数是决定性的"这个概念。bili_search_hot_videos 的 keyword 可选，留空返回全站热门；get_bgm_daily_schedule 的 day 默认 today。我们的 can_direct_call 只能看
required，于是无参直调必然永远走默认值。

3. 返回值是"给 LLM 看的长文本"，没有结构，也没有摘要约定。
所以我们只能 300 字符硬截断，把 Top-10 列表切在第 4 条中间。

4. AstrBot 插件是"自己会说话的功能模块"。
handler 内部可以 event.send()、event.bot.call_action()。这意味着：工具能绕过 Stellamarizer.py 里那个 has sent the result directly to the user占位就是这个问题的痕迹）；也意味着没有真实 event 的路径（主动发言）上工具永久不可用。

一句话总结：AstrBot 的插件协议是为"单一 LLM + 全量工具注入 + 插件可直接回复"设计的；Stella 是"Router 预选 + 隔离执行 + 只回数据"。字段可以复用，语义不能复用。

对两个选项的评估

选项 B（强行适应）：日志就是它的成绩单。 今天看到的 0.007 余量、1 例工具假阳、300 字符截断、每条 2.5s 的路由税，全部是"继续让 AstrBot 的 description 当路由原型 + 继续自动派生 + 继续无参直调"的直接产物。这条路的天花板已经量出来了，不建议继续。

选项 A（自研一套 + 逐步移植）：方向对，但范围划错了。
你的核心观察——"真正值得移植的插件很少，移植成本可接受"——我认为是这个决策里最重要的事实，而且它成立的话，结论就很清晰：兼容层的价值是"可选性"，不是"吞吐量"。一个价值在于可选性的东西，应该便宜地留着
，而且绝不能对核心收费。现在它在对核心收费（收路由质量）。

但 A 里"自己参照 AstrBot 的注入原则再设计一套相似逻辑"这半句是浪费。装饰器注册、llm的参数过滤/超时/异步生成器归一/钩子分发——这些是上游多轮实测对齐出来的行为细节（落地方案 §0 第 2 点专门强调过"重写一定漏"）。重写它换不来任何路由质量的改善，因为路由质量的问题根本不在执行层。

我的建议：声明优先 + 原生工具通路

不是 A 也不是 B，是把 A 的移植路线只用在该用的地方，同时把兼容层降级为二等公民。分三步，成本递增：

第 1 步（半天，纯配置 + 一个开关）：声明优先

config/capabilities/*.toml + capability/loader.py 已经写好了，只是一条声明都没写（ 策略只有一句：自动派生的 tool.*不再进入语义路由（降级为仅显式指令可用，plugin_handler 那条确定性分发通路本来就在），只有写了声明的能力才参与竞争。

然后给这 5 个工具写 2~3 个能力声明，examples 用中文问句：

- anime.recommend ← bgm_recommend_hot_subjects：examples 写"有什么新番推荐"/"最近有
- anime.schedule ← get_bgm_daily_schedule：examples 写"今天更新什么"/"星期几放送什么"，keywords 写"放送""更新表"
- video.hot ← bili_search_hot_videos：examples 写"B站热门"/"最近有什么火的视频"

这一步同时关掉今天的三个问题：
- 假阳：候选集从 5 降到 2~3，且"新番推荐"不会再和"B站热门视频"打成 0.606 vs 0.44；
- 排序错：anime.recommend 的 examples 是问句，"推荐一些新番"会命中它而不是 schedule
- 0.007 余量：examples 是问句，与无关问句的相似度低于"当用户…时调用"这种指令句与任意句子的基线相似度，所以正样本上移、负样本下移，区间会拉开。
- 顺带打开 Level 0 零延迟通路（keywords），把一部分消息从 2.5s 的 embedding 里救出来。

这一步是可测的，别凭 5 条样本调阈值——python -m capability.router.benchmark 已经写好，四类错误分开计数。先拿基线，改完再跑一次。

第 2 步（结构级，小）：落地 kind=native

CapabilityProvider.kind 里 KIND_NATIVE 的口子已经留好了。这一步就是你说的"自己设计 的工具，不推翻兼容层：

- 函数签名直接是 Python 参数，不经过 event；
- 返回结构化结果（数据 + 一个 summary 字段），从源头解决 300 字符截断；
- 声明里带"决定性参数"和"是否允许直调"，从源头解决 required 判据不足；
- 不能 event.send()，也就不会绕过 Stella 的人格。

移植一个 AstrBot 插件 = 抄它的 API 调用逻辑（那才是真正的价值所在）+ 包成 native to 接受"落地的地方，而且比"重写加载层"便宜得多。

第 3 步（保留，不动）：AstrBot 兼容层继续存在

它的价值变成两件事：能 drop-in 跑原版插件（试用、临时需求、还没顾上移植的），以及复  native 通路。不要删。做完第 1 步之后它不再对路由质量收费，代价就归零了。

一条独立于 A/B 的问题

不管选哪条路，每条消息 2.5s 的 embedding 税都不会自动消失，而且现在 5 轮里 3 轮是纯交的动作：

1. 先做"这句话需要外部数据吗"的粗筛，再选能力。 只有粗筛为是才付 embedding 的钱。目 时拍板，其余全部下沉到 L1 —— 而"要不要动用外部能力"这个二分类，本来就是 Level 0该做的事（方案 §8 说 L0 的职责是"处理高置信度请求"，"不需要工具"同样是高置信度结论）。
2. 把 embedding 挪到独立实例/端口，或关掉 LLM_SCHEDULER_GATE_EMBEDDING，消掉模型换入换出。settings.py:385 的注释里已经写了"可指向同一实例的多模型或独立端口"，这条路是设计里预留过的。
