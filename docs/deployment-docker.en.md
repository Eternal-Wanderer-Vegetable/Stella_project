# Docker Deployment Guide

[中文](deployment-docker.md) | English

> Note: This document is kept in sync with the Chinese version; in case of divergence, [deployment-docker.md](deployment-docker.md) is authoritative.
> Intended use case: running Stella long-term on a remote Linux server (or any machine with Docker).
> Design rationale: [`design_docs/Docker 化部署方案 v1.0.md`](../design_docs/Docker%20化部署方案%20v1.0.md) (Chinese).
> Windows desktop deployment (Stella.exe / start.bat) is unaffected; see the [README](../README.en.md).

## 1. Architecture and Boundaries

Recommended topology (the default compose form): **two containers on one host** -- NapCat and Stella on the same server, with the reverse WebSocket going over the compose-internal network, so **no public ports are occupied**:

```
Server (docker compose)
┌──────────────────────────────────────────┐
│  stella container                napcat container             │
│   STELLA_HOME=/data              WebUI 6099 (loopback only)  │
│   ./StellaData ←─bind mount     reverse WS client ─────┐     │
│   listens on 8080 ←────────────────────────────────────┘     │
└──────────────────────────────────────────┘
     LM Studio / online APIs (outbound from Stella, not in compose)
```

Alternative topology: **NapCat on another machine** (e.g. NapCatQQ Desktop on your own Windows PC) -- change `stella.ports` in the compose file to `"8080:8080"`, and be sure to configure `ONEBOT_ACCESS_TOKEN` and TLS as described in §6.

The image contains only the **program**; all user data lives in `./StellaData/` on the host (mounted at `/data` in the container):

| Data | Location (under StellaData/) | Notes |
|---|---|---|
| Configuration (incl. API keys) | `.env` | Generated by the `deploy init` wizard, or copied from an existing install |
| Memory store | `memory/agent_memory.db` | SQLite; all chat memory lives here |
| Plugins / plugin data / render cache | `data/` | AstrBot ecosystem plugins work by unzipping them here |
| Group-space config / persona | `config/spaces/`, `system_prompts/` | Factory personas are built into the image; put your customized copy here, it takes priority |
| Logs | `logs/` | Includes the boot diagnostics `boot_debug.log` |

Hence two ground rules: **upgrade = swap the image, data stays put**; **backup = archive `StellaData/`**.

## 2. Prerequisites

- Server: Docker ≥ 20.10 and docker compose v2 (`docker compose version` prints a version)
- Memory ≥ 1 GB (the image is about 1.2 GB, including the Chromium and CJK fonts used for rendering)
- Decide on model endpoints (trade-offs between the three modes: see [README · Three Deployment Modes](../README.en.md#-three-deployment-modes)):
  - **All-online**: just fill in online API addresses -- simplest;
  - **Hybrid / all-local**: if LM Studio runs on the same host, fill in `http://host.docker.internal:1234` as the endpoint (compose already configures `host-gateway`); if it runs on another machine, use that machine's internal address directly.

## 3. Quick Start (first deployment)

```bash
# 1) Get the code (git clone, or upload from your machine; note that .env is not in git,
#    it does not travel with the repository)
git clone https://github.com/Eternal-Wanderer-Vegetable/Stella_project.git
cd Stella_project

# 2) Prepare the data directory (the container runs as uid 1000; on Ubuntu the first user
#    is usually 1000, so it is often writable out of the box)
mkdir -p StellaData
sudo chown -R 1000:1000 StellaData   # when in doubt, run this -- always correct

# 3) Build the image (on servers in China you can add
#    --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple,
#    but some Chinese mirrors do not carry playwright; if it fails to install,
#    drop the argument and fall back to the official index)
docker compose build
#    You can also skip the build and use the official image: in docker-compose.yml,
#    swap the stella service's build/image lines for the GHCR line (see the comments
#    in that file), then run: docker compose pull stella

# 4) First-time configuration: interactive wizard (keep the listen port at the default
#    8080; also group numbers, model endpoints and keys); writes StellaData/.env
#    ⚠ When the wizard asks for the "listen address", make sure to enter 0.0.0.0
#    (the default 127.0.0.1 is for the Windows desktop scenario; inside a container
#    NapCat cannot connect to it -- if you forget, the container warns loudly at startup)
docker compose run --rm stella python -m deploy init

# 5) Start and confirm health (the stella STATUS column must show healthy;
#    napcat counts as started even before login)
docker compose up -d
docker compose ps

# 6) NapCat first login and network configuration (manual, once only):
#    a. SSH tunnel into the WebUI: locally run ssh -L 6099:127.0.0.1:6099 user@<server>,
#       then open http://127.0.0.1:6099/webui in a browser (the WebUI is bound to the
#       server's loopback only; it cannot be opened without the tunnel)
#    b. The WebUI login token is in the container logs: docker compose logs napcat | grep -i token
#    c. Scan the QR code in the WebUI to log into QQ
#    d. Network configuration → add a "WebSocket client":
#       URL   = ws://stella:8080/onebot/v11/ws (the compose service name resolves as a hostname)
#       token = the value of ONEBOT_ACCESS_TOKEN from .env (leave empty if not set)
```

If you already have a working `.env`, skip step 4 and place the file at `StellaData/.env` directly.
Follow-up troubleshooting: `docker compose logs -f stella` (runtime logs), `docker compose exec stella python -m deploy doctor` (environment self-check), `StellaData/logs/boot_debug.log` (boot-time plugin-loading diagnostics).

## 4. Migrating from an Existing Windows Install

1. Stop the local Bot (`stop.bat` or via the GUI);
2. Copy the following into `StellaData/` on the server (paths relative to the old install's data directory):

   | What | Where | If skipped |
   |---|---|---|
   | `.env` | `StellaData/.env` | All configuration and keys lost; init needed again |
   | `memory/agent_memory.db` (and `.bak` backups) | `StellaData/memory/` | Memory wiped |
   | `data/plugins/`, `data/plugin_data/` | `StellaData/data/` | Plugins lost |
   | `config/spaces/` | `StellaData/config/spaces/` | Group-space config falls back to defaults |
   | `system_prompts/` (only if you customized the persona) | `StellaData/system_prompts/` | Falls back to the factory persona baked into the image |

3. If `.env` contains `127.0.0.1`/`localhost` model endpoints, change them to `http://host.docker.internal:1234` (when LM Studio runs on the same server host) or the real address;
4. Continue at step 5 of §3 to start the containers.

`logs/` is optional (historical logs; does not affect operation).

## 5. Day-to-Day Operations

```bash
docker compose stop            # stop (SIGTERM → 5s graceful shutdown; in-flight memory consolidation is not lost)
docker compose start           # start
docker compose restart         # restart
docker compose logs -f stella  # follow logs

# Upgrade (the data volume stays untouched -- that is the payoff of the STELLA_HOME design)
git pull
docker compose build          # local-build setup; when using the official GHCR image:
docker compose pull napcat    #   docker compose pull stella && docker compose pull napcat
docker compose up -d

# Backup (stopping first is safest; for a hot backup, run the self-check via
# docker compose exec stella python -m deploy doctor first, then archive)
docker compose stop
tar czf stella-backup-$(date +%F).tar.gz StellaData/
docker compose start

# Restore = unpack over StellaData/, then up -d
```

## 6. Security Checklist

- **When exposing 8080 to the public internet, a token is mandatory**: set `ONEBOT_ACCESS_TOKEN=<random string>` in `.env` and the same value in the NapCat WebUI. Without a token, anyone who knows the address can impersonate a QQ client and control the Bot.
- Better yet, do not expose it bare: put Caddy/Nginx in front for TLS (WebSocket reverse proxy), or use WireGuard/Tailscale, and bind the compose `ports` to `127.0.0.1:8080:8080`.
- `StellaData/.env` and the memory store contain API keys and chat logs: `chmod 600`, keep them out of git, and never bake them into the image (`.dockerignore` already guards this).
- The server firewall should only open the ports you need: in the default compose setup, stella 8080 and the NapCat WebUI 6099 are both bound to `127.0.0.1` -- zero public exposure; remote access always goes through an SSH tunnel or WireGuard.

## 7. FAQ

| Symptom | Cause and fix |
|---|---|
| `docker compose ps` shows `unhealthy` | The in-container probe of `127.0.0.1:8080/stella/status` failed. Check `docker compose logs stella` first to see how far startup got; commonly `.env` is missing or a model endpoint is unreachable (the probe itself does not depend on models, so usually the process failed to start) |
| `curl :8080/stella/status` on the host returns 403 | Expected: the endpoint only accepts loopback clients, and 403 actually proves the HTTP server is alive. External monitoring should treat "not 000/timeout" as alive, or probe from inside the container |
| Chinese characters in rendered cards turn into boxes | Should not happen -- CJK fonts are baked into the image. It only happens with hand-rolled slim images that dropped `fonts-noto-cjk` |
| Proactive-chat timing is all wrong | Check `TZ` (the image defaults to `Asia/Shanghai`; override in compose) |
| `deploy init` cannot write to `/data` | The host directory's owner is not uid 1000: `sudo chown -R 1000:1000 StellaData`, or switch to a named volume (see below) |
| pip fails to install playwright | The mirror you use does not carry playwright; drop `PIP_INDEX_URL` to fall back to the official index (same note as in `requirements.txt`) |
| Want a different port | Change the compose mapping (e.g. `"9090:8080"`); do **not** change `PORT` in `.env` -- the in-container health check and the NapCat reverse-WS address are both anchored to 8080 |
| The container exits right after starting; logs mention `/data/.env 不存在` (not found) | Expected behavior (entrypoint gate): follow the log hint and run `deploy init` or place `.env`. To force a dry run with empty config for debugging: `docker compose run --rm -e STELLA_SKIP_ENV_CHECK=1 stella` |
| stella shows healthy but NapCat keeps failing to reconnect | Nine times out of ten `HOST=127.0.0.1` in `StellaData/.env` (the wizard default, a Windows desktop assumption): the in-container health check goes over loopback so it stays green, but NapCat cannot get in. Change to `HOST=0.0.0.0` and restart; the container startup logs contain a matching warning |
| Small-memory server that does not need image rendering | Build the slim image: `docker build --build-arg WITH_RENDER=false -t stella:slim .`, saving roughly 300 MB. Render requests take the existing degradation path (no rendering, warning only); everything else is unaffected |
| NapCat WebUI (6099) will not open | It is bound to the server's loopback only: first `ssh -L 6099:127.0.0.1:6099 user@<server>`, then visit `http://127.0.0.1:6099/webui` locally; the login token is in `docker compose logs napcat` |

**Named volume instead of a bind mount**: when you do not want a host directory (or keep hitting permission trouble), change the compose mount to `stella-data:/data` and append at the end of the file:

```yaml
volumes:
  stella-data:
```

Data is then managed by Docker (find the location via `docker volume inspect stella_stella-data`); back it up with `docker run --rm -v stella_stella-data:/data -v "$PWD":/backup alpine tar czf /backup/stella-data.tar.gz -C /data .`.

## 8. Boundaries and Limitations

- **Single instance only**: the memory store is a local SQLite database plus in-process state. Do not `docker compose up --scale stella=2`, and do not share one data directory across machines.
- `PORT` inside the container is fixed at 8080 (rationale and alternatives in §7).
- NapCat's login state lives in `./napcat/QQ/` and its network configuration in `./napcat/config/` -- include both in backups alongside `StellaData/`; if lost you need to re-scan the QR code and re-configure WS respectively.
- QQ risk-control note: scanning a QR code to log in a new device from a datacenter IP may trigger a security review. That is QQ-side policy and unrelated to this project; if it keeps failing, leave NapCat running in your usual network environment and switch to the alternative topology in §1.
