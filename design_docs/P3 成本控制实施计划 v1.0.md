# P3 成本控制实施计划 v1.0

> 母方案：[`在线 LLM 接入方案 v1.0.md`](在线%20LLM%20接入方案%20v1.0.md) §10 路线图的 **P3** 行（成本控制）。
> 本文件是该行的落地细化：Tier 0 余项 + Tier 1 前置过滤 + Tier 2 记账/预算 + 用量面板 + 降级链补口。
> P3 作为独立发布版本发布。

---

## Context

`design_docs/在线 LLM 接入方案 v1.0.md` 的 P0/P1/P2 已落地并提交，文档也已同步。P3 是最后一档：**成本控制**。

问题：P2 之后接在线端点已经可用，但**花了多少钱不可见、也不可控**。记忆域（整合 / 压缩 / 提取）是高频低难度任务，在在线端点上会持续烧 token；前缀缓存（P0-3 / T0-1）是否真的命中，目前没有任何观测手段；一旦配置失误或群聊突然活跃，账单没有上限。

P3 交付后应满足设计文档 §10 的验收标准：

- 缓存命中率与 token 用量在 GUI 可见
- 每日预算生效
- **超额只暂停记忆域，对话照常可用**

P3 作为**独立发布版本**发布。

## 不可违背的约束（先读这一段）

这几条是设计文档与既有测试面共同锁定的，违反任何一条都会造成回归或数据丢失：

1. **所有「跳过」路径都必须不推进 checkpoint。** 设计文档原文：「否则就是 P0-4 的另一种形态（消息永久丢失）。跳过 = 攒批，不是丢弃。需要一个『连续跳过上限』兜底，避免某群永远攒不够而无限滞留。」
2. **400（请求体错误）不降级。** 「那是配置问题，降级只会掩盖它。」契约已写在 `config/settings.py:960-961` 与 `core/llm/lm_studio.py` 的注释里，但 `RoleBackend` 没有执行它。
3. **`_generate()` 保持 6 元组返回。** 设计文档第 207 行明确禁止加第 7 个元素——`test_consolidator_core.py` / `test_full_workflow.py` / `test_short_term_attribution.py` 里有 5 处 monkeypatch 假后端按 6 元组写死。
4. **`_fetch_next_messages()` 保持 4 元组返回。** `tests/test_bot_self_source.py`、`tests/test_source_kind.py`、`tests/test_consolidator_core.py` 共 8 处按 4 元组解包。
5. **记账绝不能成为聊天链路的失败点。** `core/llm/usage_sink.py` 的模块契约：全程吞异常、零 DB 依赖。
6. **`SCHEMA_VERSION` 每 +1 必须同时提交 `migrate_vN` 与一个旧库夹具回归测试**（`memory/schema.py` 模块 docstring 的硬规矩）。
7. **新增 doctor 检查在健康快照下必须返回 `None`**——`tests/test_deploy_checks.py:83` 断言健康快照全部计为 ok。
8. **`status_api` 响应体不含任何凭据与群聊内容**——用量面板只暴露计数与比率，绝不含 prompt / 模型输出。

## 阶段 A：Tier 2 记账与预算（先做，面板与 doctor 都依赖它）

### A1. 新表（SCHEMA_VERSION 10 → 11）

- `memory/schema.py`：按既有新表范式加 `_LLM_USAGE_DAILY_TABLE_DDL` 常量 + `create_llm_usage_daily_table(conn)` 包装，在 `_migrate()` 里用 `contextlib.suppress(sqlite3.OperationalError)` 调用并受 `if not dry_run` 保护；`SCHEMA_VERSION` 改 11。
  - 表：`llm_usage_daily(date TEXT, role TEXT, slot TEXT, model TEXT, kind TEXT, calls INT, failures INT, prompt_tokens INT, completion_tokens INT, cached_tokens INT, PRIMARY KEY(date, role, slot, model))`
  - **不要**加进 `GROUP_SCOPED_TABLES`——它不按群归属，空间合并不该碰它。
- `memory/migrations.py`：加 `migrate_v11`，照抄 `migrate_v9` 的极简新表范式（lazy import + 调 `create_*` + 返回 `MigrationResult`），注册进 `MIGRATIONS`。

### A2. 账本与预算判据（新文件 `core/llm/usage_store.py`）

放在 `core/llm/` 而不是 `memory/`：`memory/embeddings.py` 已经反向 import `core.llm`，模块级 `core.llm → memory` 会成环。**DDL 仍留在 `memory/schema.py`（单一真源），在 flush/load 函数内部 lazy import。**

- 内存缓冲 `dict[(date, role, slot, model)] → 计数`，周期性 + 读取时 + 退出时 UPSERT 落盘。**不在每次 LLM 调用里同步写 SQLite**，这是约束 5 的要求。
- 进程启动时从表里读回**今日**累计，重启不清零预算。
- 启动时顺带 `DELETE FROM llm_usage_daily WHERE date < <90天前>`（不设配置项，写死 90 天并在文档说明）。
- 日期键用**本地时区** `datetime.now().strftime("%Y-%m-%d")`——设计文档要求「用日期键而非计时器」。
- 通过 `usage_sink.set_sink()` 挂上（那是文档里指定的落点，本来就是为 P3 留的空函数）。`UsageRecord` 已带 `kind`，预算域 `online` 直接按它过滤，不必回查 registry。
- 导出 `budget_blocked(role) -> str | None`（返回人类可读原因或 None）与 `usage_snapshot() -> dict`。

### A3. 配置项（`config/settings.py`，紧跟现有 `# ---------- LLM 角色（Role） ----------` 段之后）

| 键 | 默认 | 说明 |
|---|---|---|
| `LLM_USAGE_ACCOUNTING` | `true` | 关掉则完全不写库、不挂 sink |
| `LLM_DAILY_TOKEN_BUDGET` | `0` | 0 = 不限 |
| `LLM_BUDGET_SCOPE` | `online` | `online` 只算在线端点 / `all` |
| `LLM_BUDGET_EXHAUSTED_ACTION` | `pause_memory` | `pause_memory` / `pause_all` / `warn_only` |

新键经 `deploy/env_schema.py` 的 AST 扫描自动出现在 GUI 高级选项表单里，无需改前端；但必须写成字面量 `_env*("KEY", ...)` 调用并放在正确的注释分区下。

### A4. 预算在哪里生效

在**各域入口**显式判据，不在 `registry.backend_for()` 里做——那里有实例缓存且被大量测试 monkeypatch。

- `memory/consolidator.py::consolidate_group`——`_generate` 之前（CONSOLIDATION）
- `memory/consolidator.py::_extract_candidates`——入口（EXTRACT）
- `memory/session_compact.py::compact_once`——入口（COMPACT，落在 `_backend()` 取用之前，复用该函数已有的「端点未配置」降级返回路径）

`pause_memory`（默认）只拦这三处，对话链路一行不改 → 直接满足「对话照常可用」。

`pause_all`（非默认，用户显式选择的硬停）额外拦聊天链路：**跳过 LLM、静默不回，只写一条 warn 日志**。语义最干净——pause_all 就是「一分钱都别再花」；群里看起来像 Bot 下线是这个选项的既有代价，不额外发提示句、也不回落到本地端点（回落会让「全停」名不副实，且纯在线部署下本来就没有本地端点可落）。落点在 `ai_gateway.py` 的回复生成前（`pipeline.run(ctx)` 之前，`memory/consolidator.py` 的 force 触发之后），沿用 NoneBot 的正常「不回复」返回路径，不抛异常。

## 阶段 B：Tier 1 前置过滤

### B1. 纯逻辑模块（新文件 `memory/cost_gates.py`）

判据全部做成**无 DB、无 I/O 的纯函数**，这样 `tests/test_cost_gates.py` 不用搭库：

- `is_trivial_line(text)`——图片 / 表情 / 单字应答
- `should_skip_by_source_ratio(at_senders, lines)`（T1-1）
- `at_mention_slice(messages_text, context_lines)`（T1-2）
- 语义新颖度判据（T1-3/T1-4）的编排入口

复用现成件，不要重写：
- **T1-4**：`memory/text_similarity.py` 的 `is_similar(a, b, threshold=0.65)` / `normalize_text`
- **T1-3**：`memory/embeddings.py` 的 `EmbeddingService.similarity(query, content)`（任何失败返回 None 的降级契约已内建），构造范式照 `memory/retrieval_v2.py:443` 的 lazy import
- ⚠️ **`MEMORY_EMBEDDING_ENABLED` 默认 `false`**（`config/settings.py:412`）。所以 T1-3 拿不到向量时必须落到 T1-4 的词面判据，否则这道闸在默认配置下永远不触发。

### B2. 接进 consolidator（不动任何既有签名）

- 新增**加法式**方法 `_peek_batch(group_id, last_id, limit)`，只读同一窗口返回统计（`at_count` / `trivial_count` / `total`），供 T1-1 在**调 LLM 之前**判断。多一次本地 SQLite 读 ~30 行，代价可忽略；这样 `_fetch_next_messages` 的 4 元组不用动（约束 4）。
- T1-2：把 `_fetch_next_messages` 里写 AT_MENTION 标记的字面量提成模块级常量，读写共用一个常量，然后 `_extract_candidates` 内部按行切片。**不加第 7 个元组元素**（约束 3）。
- T1-5：`consolidate_group` 现有阈值分支（`memory/consolidator.py:426-429`）改为按端点类型选阈值。
- **每条跳过路径都只 `return`，绝不写 checkpoint**（约束 1）。

### B3. 连续跳过上限

- `consolidation_state` 加一列 `skip_streak INTEGER NOT NULL DEFAULT 0`——走 `memory/schema.py` 的**加列**机制 + consolidator 里 `_ensure_state_table` 的 ALTER-with-suppress 范式（照 `recent_exchanges` 那处写）。加列不违反 `GROUP_SCOPED_TABLES` 的「迁移绝不触碰」——那条禁的是改归属/改名，不是加列。
- 新键 `CONSOLIDATION_MAX_SKIP_STREAK`（默认 3）：连跳到上限就强制跑一次并清零。

## 阶段 C：Tier 0 余项

先在 `core/llm/registry.py` 加一个 `role_is_online(role) -> bool`（内部 `endpoint_of(role).kind`），作为「这个角色是不是在线」的**唯一判据来源**——阶段 B/C 与预算域 `online` 共三处要用，遵循 `deploy/checks.py` 里那条「解析规则只该有一份」的原则。同时在 `core/llm/__init__.py` 补出口（该文件是门面，`memory/session_compact.py` 等都从它 import）。

三个 `CONSOLIDATION_ONLINE_*` 新键，命名与现有 `CONSOLIDATION_[LOCAL_]*` 一一对应，只在 `role_is_online(ROLE_CONSOLIDATION)` 为真时取用；填成与本地键相同的值即可关掉对应行为：

| 键 | 默认 | 对应 |
|---|---|---|
| `CONSOLIDATION_ONLINE_OVERLAP` | `0` | **T0-2** 在线不需要重叠窗口，连续性由已经在传的 `current_summary` 承担。落点 `memory/consolidator.py:557` |
| `CONSOLIDATION_ONLINE_BATCH_SIZE` | `60` | **T1-5** 加大批量。⚠️ **绝不拉长 `CONSOLIDATION_SCHEDULE_INTERVAL`**（§5.2：厂商前缀缓存是分钟级 TTL，间隔要保持 ≤ 4 分钟） |
| `CONSOLIDATION_ONLINE_FORCE_BATCH_SIZE` | `30` | **T0-5** force 路径批量与常规对齐（本地仍是 10） |

**T0-4 输出瘦身**（无需新键）：收紧 `LLM_ROLE_CONSOLIDATION_MAX_TOKENS` 的建议值（写文档，不改默认），并删掉阶段 1 prompt JSON schema 里**解析器从不读**的字段。做法：拿 schema 字段逐个对 `memory/consolidator.py` 的解析函数 grep，只删确实没有读者的。这一步安全的前提是 P0-4 的截断阶梯已经修好。改完必须跑 `tests/test_prompt_cache_prefix.py`（前缀顺序守卫）。

T0-5 的延迟风险已从代码排除：`maybe_consolidate`（`memory/consolidator.py:1142`）走 `asyncio.create_task`，`ai_gateway.py:417` 的 force 触发是 fire-and-forget，不进 @ 回复的关键路径。把 force 批量从 10 提到 30 只会让摘要新鲜度稍滞后，不会让 @ 变慢——设计文档 Q5 的顾虑在此范围内不成立。

python -m pytest tests -q            # 全量；顺带取一个准确的用例数替换 README 里的「1300+」

python -m deploy migrate --dry-run   # v10→v11 在库副本上真跑一遍

端到端手工验证（需真实在线端点）：

1. 配一个在线 CONSOLIDATION 端点 + `LLM_DAILY_TOKEN_BUDGET` 设一个很小的值
2. 启动 → GUI「运行状态」页应出现用量面板，跑几轮后**缓存命中率非 0**（这是 T0-1 真的生效的唯一证据）
3. 用量撞破预算 → 记忆整合停止并有日志，**群里 @ Bot 仍能正常回复**（默认 `pause_memory`）；再把动作改成 `pause_all` → @ Bot 静默不回、日志有 warn
4. 重启进程 → 今日累计从库里读回，不清零
5. 把在线 key 改错触发 401 → 降级到本地生效；把请求体弄成 400 → **不降级**，报错原样冒出来

## 实施结果（2026-08-30）

阶段 0 ~ F 全部落地。自动化验证：`pytest tests -q` → **1460 passed, 5 skipped**；`ruff check .` 全过；schema v10 → v11 在真实库副本上跑通（新表 `llm_usage_daily` 12 列就位，版本推进到 11）；`python -m deploy doctor` 三个新检查在当前环境下不报（健康快照全 ok 的不变量未被破坏）。

与计划有偏差的两处，记在这里以免将来误读：

- **T0-4 的「删掉解析器从不读的字段」是个空操作。** 按计划把阶段 1 prompt 的 JSON schema 字段逐个对解析函数核了一遍，**17 个键全部有读者**，没有可删的死字段。只交付了它的文档半边：在 `docs/configuration.md` 建议在线端点把 `LLM_ROLE_CONSOLIDATION_MAX_TOKENS` 收到 800（不低于 600，截断会让 JSON 解析失败），**默认值不动**——本地推理不计费，没有收紧的理由。
- **`consolidation_state.skip_streak` 只走 consolidator 的 ALTER-with-suppress，没有进 `memory/schema.py`。** 计划原文提了两处，但 `consolidation_state` 与 `short_term_context` 都是 consolidator 自己建的表，`schema.py` 的 `_ADDITIVE_COLUMNS` 里从来没有它们——`recent_exchanges`（计划点名的先例）就是这么加的。照先例写，不给 schema.py 引入它管不到的表。

另外在真实库副本上跑迁移时暴露了一个**与 P3 无关的既有问题**：开发机那份库在 v10 就已经有 `memories_fts` 索引 116 行 vs active 记忆 115 行的漂移（全部记忆恰好 116 条，说明有一条已归档的记忆还留在索引里），迁移收尾校验会为此报错。v11 只建新表、不碰 FTS，不是它造成的。

端到端手工验证（上面 5 步）需要真实在线端点，留给发布前的人工验收。
